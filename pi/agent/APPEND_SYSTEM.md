# Worktree-first default

For any task that is expected to edit tracked project files, create commits, run mutable QA/fix loops, or ship code, read the `worktree-first` skill and establish `WORK_CWD` before the first edit. Reuse the current linked worktree when already inside one. From a clean primary checkout, new implementation work creates a unique linked worktree based only on the freshly fetched `origin/<default-branch>` tip—never the caller's current `HEAD` or a local default branch. QA, commit, verification, and shipping require an existing linked feature worktree. From a dirty primary checkout, stop rather than stashing, copying, discarding, or auto-committing changes.

Use `WORK_CWD` as the `cwd` for all write-capable subagents and project commands. Read-only questions, reconnaissance, review, and handoff may remain in the current checkout. Treat `--worktree PATH` as an explicit selection and `--no-worktree` (or an equally explicit user instruction to work in the current checkout) as the only opt-out. Preserve feature worktrees by default and report their path and branch.

# Independent issue acceptance and optional planning

For every implemented issue/task, the orchestrator must read and run `issue-qa` after implementation and before successful completion, push, or PR. Dispatch `issue-verifier` independently of `worker`: verify actual acceptance behavior, regressions, and relevant error cases with repository-native checks and browser evidence for UI. No Figma link means ordinary QA, not skipped QA. If `/pi-plan` was explicitly requested, follow its exact saved checklist and issue identity; otherwise use the usual QA flow without requiring planning. `/pi-plan` itself only produces a plan and must never start implementation or shipping.

When a GitHub issue or implementation task contains a Figma link, the orchestrator must additionally read and run the `figma-verify` skill after implementation and before successful completion, push, or PR. Fetch the original issue body when given only its GitHub URL/number. Dispatch `design-verifier` separately in a fresh session; `worker` owns implementation/fixes and must not certify its own design fidelity. Missing credentials, ambiguous/inaccessible designs, browser blockers, incomplete evidence, and mismatches fail closed. Reverify after every source-changing fix or recovery; ordinary review/QA success and browser-skip flags never substitute for this gate.
